# How it works

Building and using it are described in the [README](../README.md),
`docs/switch/` and `docs/linux/`. This document is about the core both share;
what's specific to the Switch is in [switch/internals.md](switch/internals.md).

The idea, and most of the machinery described here, comes from
[ftl-android](https://github.com/Sidd065/ftl-android) by Sidd065: the Mach-O
loader, the Objective-C runtime, the iOS frameworks and the touch layer. This
project took that core off Android and onto Linux and the Nintendo Switch. [CREDITS.md](../CREDITS.md) lists what came
from where.

## The short version

Nothing is recompiled. The original arm64 iOS executable of FTL for iPad runs
as it is, inside a normal program (a Linux program, or a Switch homebrew `.nro`):

1. The **Mach-O loader** maps the game's executable into memory and links its
   imports against the port's own replacements.
2. Underneath the game is just enough of iOS for it to run: a C library with
   Darwin's ABI, an **Objective-C runtime** with Apple's ABI, Apple's C++
   library ABI, and small reimplementations of the **iOS frameworks** the game
   uses (UIKit, Foundation, QuartzCore/OpenGL ES, AudioToolbox, ...).
3. A **platform layer** connects all of that to the host: SDL3 on Linux,
   libnx on the Switch, with EGL/GLES 3 for drawing on both.
4. A **UX layer** adds what the iPad game doesn't have on a desktop: mouse,
   keyboard and controller input, zoom, the magnifier, and help for PC mods.

The game believes it is on an iPad whose screen has the window's shape.

## Layers

```
native/src/
  platform/switch/ ftl.nro: libnx, EGL on mesa, touch, Joy-Cons, applets, code
                   memory under Horizon, mods with ftlman's engine
  platform/linux/  ftl-linux: SDL3 window, EGL, input, audio, dialogs, settings.ini,
                   import, portable folders, ftlman, logs (main_linux.c, plat_sdl.c);
                   import, settings, zip reading and mods are shared with the Switch
  ux/              layout, zoom, gestures, magnifier, minimap, hotkeys, controller
                   cursor, mods' images and atlases, PNG
  fw/              UIKit, Foundation, QuartzCore/EAGL, AudioUnit, GameKit and
                   GameController stand-ins
  objc/            Objective-C runtime with Apple's ABI (objc_msgSend in assembly)
  darwin/          libSystem: Darwin structs, pthreads, Mach semaphores, errno
  loader/          Mach-O loader: maps the arm64 slice, rebases, binds imports;
                   executable memory through execmem.h
  port_main.c      boot sequence: frameworks, load, bind, patch, protect, run main()
  patches.c        hooks into the game's code (only for the 1.6.21 build)
  hyperspace.c     starts Hyperspace, when the applied mods include it
```

`port_main.c` shows the order everything happens in: the frameworks are set up,
the executable is loaded and bound, the 1.6.21 patches are applied, the image is
protected, the game's Objective-C classes are registered, Hyperspace (if wanted)
hooks the game, the game's static initializers run, and finally its `main()` is
called, which calls `UIApplicationMain` like any iOS app.

## The Mach-O loader (`loader/`)

`macho.c` reads the arm64 slice of the executable, copies its segments into
anonymous memory, applies rebases and binds the imports (DYLD_INFO-style
fixups, which is what the 1.6.21 build uses). Every import is resolved by
name through `symbols.c`, a table of the port's replacements for libSystem,
the frameworks and the C++ library. `symbols_cxx.c` is generated by
`tools/gen_cxx_syms.py`.

**Host page sizes.** Segments are copied, not mapped from the file, and
protections are set per host page, so the loader runs on 4K, 16K and 64K
kernels. On 64K kernels the page holding the end of `__TEXT` and the start of
`__DATA` gets both permissions (RWX): the game's code addresses its data
PC-relatively, so the segments can't be moved apart. The ELF parts are linked
with `max-page-size=65536`. This was tested on the 16K Asahi kernel, on a 4K
kernel (Asahi's `muvm` micro-VM), and with `FTL_PAGESIZE=65536`, which makes
the loader act as if pages were 64K.

**Executable memory** goes through `loader/execmem.h`: allocate, protect, and
separate write and execute views of the same code. On Linux one anonymous
mapping serves both. The Switch never allows writable code, so there the code
is written through a second view of it
([switch/internals.md](switch/internals.md#how-the-games-code-is-mapped)).

## The Objective-C runtime (`objc/`)

The game is mostly C++ but talks to iOS through Objective-C. `objc/` is a
runtime with Apple's arm64 objc2 ABI, so the game's compiled class lists,
selector references and method lists can be used as they are:
`objc_runtime.c` registers the game's classes and the port's own framework
classes, and `objc_msgSend.S` is the message dispatcher in assembly with a
lock-free method cache. `objc_api.c` has the less common entry points (ARC
helpers, properties, associated objects).

## The C library and the C++ library (`darwin/`, `libcxx/`)

iOS's C library differs from glibc in struct layouts (`stat`, `dirent`,
`tm`...), errno values, flags and some calling conventions. `darwin/libsystem.c`
translates between the two, and has pthreads and Mach semaphores built on the
host's.

The game was built against Apple's libc++, so the port links its own copy built
to match: the alternate string layout, constructors that return `this`, Darwin
ctype masks, and a libunwind that can read Mach-O compact unwind info, so C++
exceptions can cross the game's frames (`port_main.c` tells it where the game's
`__unwind_info` and `__eh_frame` are). The changes to LLVM 19.1.7 are in
`libcxx/llvm-19.1.7-ftl.patch`; `libcxx/build.sh` applies them.

## The frameworks (`fw/`)

Only what FTL uses, plus a little: 

- `uikit.c`: `UIApplicationMain`, the main run loop, a minimal view tree, touch
  events, alerts and text input (forwarded to the platform layer).
- `foundation.c`: Foundation and CoreFoundation (strings, collections,
  bundles, user defaults, file manager, dates).
- `quartz_eagl.c`: `CAEAGLLayer`, `CADisplayLink` and `EAGLContext` on top of
  GLES 3. The game renders into an FBO that `present.c` puts on the window
  (with the UX layer's zoom and overlays). BGRA textures are swizzled, and
  PVRTC textures, which iOS GPUs sample natively, are decoded on the CPU
  (`pvrtc.c`).
- `audio_misc.c`: the RemoteIO AudioUnit and AVAudioSession on the platform's
  audio output.
- `gamecontroller.c`: GameController and GameKit stubs (the UX layer drives
  controllers instead).

## Hooks into the game (`patches.c`, `ux/`)

A few features hook specific addresses in the 1.6.21 binary: the logger, the
pause action, the hotkey lookup, menu and window state, the PNG reader and the
`ftl.dat` reader for mods. `ux/game.h` has the addresses and struct offsets.
They're only enabled when the binary's `LC_UUID` matches that build, and
Hyperspace only starts on it. Other versions run without them;
`ftl-linux --info` shows the version and whether it gets them. Hook stubs jump
through `x17`, so Hyperspace can hook the same functions.

The UX layer (`ux/ux.c`, `pad.c`, `overlay.c`, `targets.c`) works on the game
image: it maps mouse, touch and controller input onto the game's touch
coordinates, zooms by drawing part of the game's image bigger, and draws the
magnifier and minimap on top. For the controller cursor, the game's thread
collects the clickable things on screen (`targets.c`), so the cursor can be
drawn to them.

## Mods

ftlman patches `ftl.dat` as on PC. The iPad build needs some help with what mods
add:

- It was built without its PNG reader, since its own art is all `.tex`
  textures. `ux/png.c` puts one back (stb_image).
- It looks for `x.tex` before `x.png`, so the ftl.dat reader hides an iPad
  texture when a mod added a PNG of the same name.
- It packs small images into atlases. At launch, when `ftl.dat` changed, the
  atlas lists without the images mods replaced are written into a small overlay
  in the cache, which the reader serves instead (`ux/mods.c`).

## Hyperspace

`hyperspace.c` loads Hyperspace's library once the game is mapped, linked and
protected, before any game code runs, and calls its `hs_android_init` with where
the game is (`hyperspace_host.h`, shared with Hyperspace's iPad branch, whose
names these are). Its logs (zhl.log, FTL_HS.log) go to the log folder with the
session logs. If it fails to start, the game doesn't start and the reason is
shown.

For mods' right clicks, `ux.c` asks it whether a script listens for the right
button (`hs_android_wants_right_click`) and, if so, sends it the touch gesture
(one finger held, a tap with another) and the mouse's right button
(`hs_android_right_button`). `hyperspace/` builds it (`linux.patch` on top of
the fork; on the Switch it is linked in, see
[switch/internals.md](switch/internals.md#hyperspace)).

The `hs_android_*` names and the `HS_ANDROID` code paths are kept on purpose:
the interface is shared with the fork's Android host, and the Linux and Switch
changes are meant to be merged back into it.
